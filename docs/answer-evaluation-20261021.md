## Подтверждённые ошибки

### Предложение меняет поведение сортировки

Агент заменил стабильную сортировку по сумме на:

```python
return sorted(result, key=lambda row: (-row['total'], row['customer_id']))
```

При одинаковых суммах и порядке появления клиентов `[2, 1]` получается
`[1, 2]`. Требовалось сохранить `[2, 1]`. Провалены один из пяти эталонных
тестов, один из двух тестов самого агента и все 50 специально построенных
перестановок клиентов с равными суммами. Двести случайных примеров без
специального построения равных итогов эту ошибку не обнаружили — отдельный
тест сохраняемого поведения оказался необходим.

Два предложенных теста представлены как функции с `self`, но без класса
`unittest.TestCase`. Для исполнения их утверждений добавлена только оболочка
класса; тела и ожидаемые результаты не изменялись. Как самостоятельный
тестовый файл первоначальный ответ неполон.

### Неправильный тест для корректного положительного фильтра

`summarize_orders_positive` сохранил Decimal и стабильную сортировку,
верно отфильтровал ноль и отрицательные итоги. Пройдены независимый тест
нуля/возврата/положительного итога и 200 сравнений с эталоном. Исходные
пять проверок базового метода также проходят при добавлении новой функции.

При этом предложенный агентом `test_zero_total` содержит суммы **2,30** и
**10,00**, но ожидает `[]`. Этот тест падает. Второй предложенный тест
отрицательного возврата проходит. Для настоящего теста нулевого итога
нужны, например, заказы `+5` и `−5` одного клиента.

### Неподтверждённые подписи SQL

В источнике у `wr.ss` и `wr.ss_V` нет описания назначения. Агент дал им
подписи «Специальность получателя» и «Специальность выписчика». Из источника
эти выводы не следуют. Таблицы, JOIN по `C_OGRN` и параметр `wr.sn_lr = ?`
сохранены верно; проверка ссылок приняла ответ. Выполнение SQL и проверка
реальной схемы медицинской базы не проводились.

### Неверная оценка сложности и испорченная ссылка

В анализе метода указано `O(n + m)` для числа заказов и клиентов. Пропущены
перебор позиций заказов и сортировка итогов. Для `C` клиентов, `O` заказов,
`I` позиций и `U` клиентов с итогами обычная оценка:
`O(C + O + I + U log U)`.

В том же ответе агент изменил UUID одной ссылки. Backend отметил её как
неподтверждённую; одна попытка исправления не устранила проблему. Несмотря
на просьбу «не переписывай код», агент включил метод целиком.

## Продолжение диалога через HTTP API

Отдельно проверены два диалога по два сообщения. Первый вопрос называет
учебный проект и `source-bundle.md`; следующий спрашивает о равных суммах.

| Уточнение | Сохранён документ | Ответ |
| --- | --- | --- |
| «Подробнее: как при этом сортируются клиенты с равными суммами? Ответь кратко со ссылкой.» — 13 слов | Нет | Найдены посторонние документы, точной ссылки нет |
| «Подробнее: как сортируются равные суммы?» — 5 слов | Да | Правильно указан порядок первого появления клиента |

В обоих диалогах история сохранила два хода. Неавторизованное чтение
возвращало 401. После проверки удалены только созданные тестовые диалоги.

Причина потери документа подтверждена локальным воспроизведением:
`AnswerSession.__post_init__` переносит выбранные документы только при
`len(tokenize(question)) <= 12` и наличии слова из короткого списка.
При 13 словах `scope_ready=False`, при пяти — `True`. Это ограничение
логики подготовки запроса, а не отсутствие нужного документа в индексе.

У короткого ответа факты верны, но блок `Sources` продублирован. Это отдельный
недочёт оформления.

## Что исправлять в первую очередь

1. Сохранять выбранный документ при смысловом продолжении диалога без
   жёсткой границы в 12 слов; сбрасывать область при явной смене темы.
2. Проверять предложения по коду на эталонных и пограничных случаях до
   признания готовыми. Проверку ссылки и проверку поведения показывать отдельно.
3. Запретить догадки о назначении полей SQL: сохранять исходное имя либо
   явно указывать, что описание отсутствует.
4. Формировать ссылки только из меток backend; не просить модель повторять
   UUID и координаты. Убирать дублирование списка источников.
5. Проверять полноту и смысл предложенных тестов. Загрузку навыка нельзя
   считать гарантированной инструкцией: в основном прогоне `load_skill`
   вызван лишь в одном сценарии, а его вызов не предотвратил ошибку сортировки.

Эти исправления в рабочий агент в рамках проверки не применялись.
Сгенерированные предложения не меняли исходники проекта.

## Артефакты и повторный запуск

Полные ответы, доказательства и журнал вызовов:
`work/answer-evaluation-20261021-37255d3f/responses.json`.
Ручные оценки: `manual-review.json`; результаты исполнения: `code-execution.json`;
журналы: `refactor/*.log`, `positive/*.log`; диалоги:
`followup.json`, `followup-short.json`; воспроизведение порога:
`followup-diagnosis.json` в той же папке. Полные ответы содержат выдержки из
рабочих документов и остаются в игнорируемой папке `work`.

Повторить основные 13 сценариев через текущий API-контейнер:

```powershell
.venv\Scripts\python.exe scripts/run_answer_evaluation.py
```

Скрипт не записывает диалоги и не меняет индекс. Он сохранит новый отчёт
в `work/answer-evaluation-<дата>-<id>/responses.json`. Ненулевой код завершения
означает ошибку запроса или непрохождение автоматической проверки; нулевой
код не заменяет сверку фактов и проверку предложенного кода. Для этого набора
нужны исходные PDF и `source-bundle.md` в доступной читателю части индекса.

Python из ответов исполнялся после просмотра в отдельных контейнерах без сети,
рабочих томов и секретов, с файловой системой только для чтения и лимитами
ресурсов. Исходный учебный метод перед сравнением прошёл свои пять тестов.
Рабочие данные после проверки: 34 версии, 43 диалога, 45 ходов, 12 заданий,
26 записей активных поколений — количество совпало с состоянием до тестов.
Проверка синтаксиса и архитектурных зависимостей также прошла.
