# Поиск и смена темы в чате — 21 октября 2026

> Исторический отчёт: первое исправление чата. Последующая проверка выявила оставшиеся ошибки.
> Числа тестов, задержки и состояние сервиса ниже относятся к этому этапу.
> Текущее поведение и последние проверки: [исправление поиска](natural-retrieval-fix.md),
> [навигатор документации](README.md).

Воспроизведены две независимые причины неверных ответов.

1. Каждый новый вопрос без имени файла считался продолжением предыдущего.
   Предыдущий вопрос и имена документов добавлялись в поисковую строку,
   а результаты ограничивались ранее выбранными документами. Поэтому новый
   вопрос мог получить старый материал либо пустую выдачу.
2. Лексический поиск различал слитные и разделённые сокращения, «е/ё».
   Точное усиление заголовка работало только при совпадении всей поисковой
   фразы с текстом. Вопрос «Какие бывают типы документов в ИС ЛО?» терял
   документ «Типы документов в ИС ЛО» среди семантически близких материалов.

Новый самостоятельный вопрос ищется без предыдущего вопроса и ограничения
старым документом. Контекст документа сохраняется для ссылок на предыдущую
реплику: «при этом», «такой порядок», «расскажи подробнее». Явное имя нового
файла и явная смена темы сбрасывают прежнюю привязку. При отсутствии ранее
выбранных документов старый вопрос не подмешивается в поиск.

Лексические признаки учитывают «е/ё» и соединяют короткие группы прописных
кириллических букв в одной строке: `АБ «ВГ»` совпадает с `абвг`. Правило общее,
без специального словаря ИСЛО. Вопросительные слова исключаются из BM25,
а заголовок, содержащийся в более длинном вопросе в исходном порядке слов,
получает приоритет. Исходный текст и embeddings не меняются; переиндексация
не требуется.

## Проверки

- 208 тестов backend прошли с отдельной временной PostgreSQL.
- 15 новых регрессионных сценариев проверяют новые темы, настоящие уточнения,
  отсутствие выбранного документа, варианты текста и заголовок среди помех.
- Прежний RAG-набор: 38/38, Recall@3 = 1, MRR@6 = 1 на отдельном индексе
  в памяти с рабочей моделью embeddings.
- Четыре последовательных запроса с настоящей моделью и рабочим индексом
  нашли и использовали ожидаемые документы: описание ИСЛО (`20119567_`),
  добавление пользователя (`1081353_`), типы документов (`53149701_`),
  преимущества перед ЕЦП (`328335378_`). Диалог в базу не записывался.
- Проверки синтаксиса и архитектуры прошли; новых циклов зависимостей нет.
- После обновления проверена настоящая HTTP-очередь `/jobs/chat`: первый
  вопрос явно выбирает инструкцию добавления пользователя, второй спрашивает
  типы документов без имени файла. Оба используют соответствующие разные
  источники; история содержит два разных ответа. Проверочный диалог удалён,
  его отсутствие подтверждено ответом 404. `/ready` возвращает 200.

Полные ответы и результаты: `work/topic-answers-verified.json`,
`work/topic-rag-evaluation.json`; сравнение поиска:
`work/retrieval-topics-before.json`, `work/retrieval-topics-after.json`.
Последний файл сравнения относится к промежуточному исправлению до усиления
заголовков; окончательная последовательность — в `topic-answers-verified.json`.

Эти проверки подтверждают поиск нужных документов и смену ответов в выбранных
сценариях. Они не доказывают точность всех утверждений модели. Определение
продолжения по языковым ссылкам остаётся эвристикой; неоднозначная реплика
может потребовать явного названия документа.

Предыдущий образ API сохранён как
`agentai-api:before-topic-fix-20261021`; идентификатор —
`work/topic-api-before-image.txt`. Обновление меняет только код API;
документы, индекс, история и конфигурация моделей сохраняются.

Исправление применено к работающему API. Две стандартные сборки получили
тайм-аут при запросе метаданных `python:3.12-slim` к `registry-1.docker.io`.
Поэтому рабочий образ собран из сохранённого локального образа с заменой
только трёх изменённых модулей в установленном пакете и `/app/src`.
Рецепт — `work/topic-fix.Dockerfile`; отчёт HTTP и контрольные суммы
исполняемых файлов — `work/http-topic-smoke.json`. Обычный `Dockerfile`
проекта остаётся пригоден для сборки при доступном Registry.
