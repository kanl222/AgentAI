# Варианты перестройки AgentAI

Дата предложения: 20 октября 2026 года. Обновление: 21 октября 2026 года.
Вариант Б реализован в исходниках; результаты и ограничения описаны в
[документе архитектуры](architecture.md). Ниже сохранены исходный анализ и план.

## Основание

План составлен по текущему рабочему дереву, включая незакоммиченные изменения.
Изучены `src/agentai`, тесты, Compose, описание продукта и два интерфейса в `web`.
Исходники сохранённого Open WebUI в `frontend` подробно не анализировались.
Анализ статический: тесты, работающая система и нагрузочные измерения в рамках
этого исследования не запускались. Обнаруженные ограничения производительности
следуют из кода; их фактическое влияние ещё нужно измерить.

## Три варианта

### А. Локальная декомпозиция

Разнести маршруты по файлам, выделить конфигурацию, авторизацию и сборку
зависимостей. Перенести разбор документов и GitLab из `core.py`, сохранив `Store`
и существующий механизм выполнения.

Порядок: фиксация поведения → сборка приложения → маршруты → разбор источников →
перенос импортов и проверка совместимости.

Плюсы: небольшой объём изменений и удобный старт. Минусы: общая изменяемая
логика ответа, чтение корпуса и ограничения исполнения остаются отдельными задачами.
Подходит, если сейчас требуется главным образом облегчить навигацию по коду.

### Б. Модульный монолит — рекомендуемый вариант

Один Python-пакет с явными модулями по возможностям. HTTP и worker вызывают одни
и те же сценарии. Модули скрывают внутреннюю механику за небольшими интерфейсами.
PostgreSQL, Qdrant, оригиналы файлов и LM Studio сохраняются на первом переходе.

Порядок: базовая проверка → независимые сценарии → конвейер ответа → жизненный
цикл индекса → единое управление исполнением → оптимизация поиска по замерам.

Плюсы: изменения можно вводить постепенно, сохраняется простое локальное
развёртывание. Минусы: потребуются пересмотр тестовых зависимостей и явное
описание транзакционных границ. Это основной объём архитектурной работы.

### В. API и отдельные процессы исполнения

Использовать границы варианта Б, затем запускать HTTP и worker раздельно.
API принимает запросы и читает состояние; worker выполняет чат и индексацию.
PostgreSQL остаётся очередью на первом этапе.

Порядок: вариант Б до стабилизации сценариев → единый вход всех GPU-операций →
отдельный запуск worker → проверка восстановления и повторного исполнения →
масштабирование по измеренным ограничениям.

Плюсы: независимый перезапуск HTTP и долгих операций, более явное владение GPU.
Минусы: усложняются доставка результатов, диагностика, остановка и восстановление.
При одной локальной GPU несколько worker сами по себе не ускорят генерацию.
Выбирать при подтверждённой потребности в раздельном жизненном цикле процессов.

## Целевая структура варианта Б

```text
src/agentai/
  bootstrap.py            # создание и закрытие зависимостей
  settings.py             # чтение и проверка конфигурации
  access/                 # личность, роли, разрешённые источники
  chat/                   # сценарий вопроса, история, результат
  answering/              # доказательства, контекст, модель, проверка ответа
  knowledge/              # поиск, соседи, версии и поколения индекса
  ingestion/              # оригиналы, извлечение, фрагменты, индексация
  execution/              # задания, исполнители, лимиты и восстановление
  adapters/               # PostgreSQL, Qdrant, LM Studio, GitLab, файловый архив
  transport/http/         # маршруты, входные/выходные модели, HTTP-ошибки
```

Внутри функциональных модулей выделяются только нужные файлы. Не создавать
одинаковые наборы controller/service/repository для каждого действия.
Общие типы размещать в модуле-владельце; не превращать `shared` в новый `core.py`.

Правило зависимостей: транспорт вызывает сценарии; сценарии используют
согласованные интерфейсы зависимостей; адаптеры реализуют эти интерфейсы;
bootstrap связывает конкретные реализации. Внутренние правила не импортируют
HTTP-маршруты, FastAPI или конфигурацию окружения.

Небольшие интерфейсы для вызывающего кода:

- `AskQuestion.execute(command, principal)` — права, контекст диалога,
  получение ответа, запись результата.
- `AnswerEngine.answer(request)` — доказательства, инструменты, модель,
  ограниченное исправление и итоговая проверка.
- `Knowledge.search(query, access)` и `read_neighbors(reference, access)` —
  только разрешённые фрагменты активных поколений.
- `IngestDocument.execute(version, principal, progress)` — разбор оригинала,
  подготовка поколения, публикация и результат.
- `Execution.submit(command, principal)` — постановка и единые правила исполнения.

Это проектируемые интерфейсы, их имена не означают уже созданные классы.
Интерфейсы адаптеров нужны там, где реально различается реализация или требуется
изолировать внешний ресурс; отдельный интерфейс для каждого класса не нужен.

## План перехода и критерии готовности

### 0. Зафиксировать исходное поведение

Сохранить существующие изменения пользователя. Выполнить автономные проверки,
отдельно PostgreSQL-тесты в выделенной тестовой БД, оценку поиска и выборочную
проверку ответов на одинаковых вопросах и доказательствах. Записать пропуски,
ошибки, версии моделей, параметры и задержки. Уточнить основной клиент:
PRODUCT.md и Compose уже описывают новый чат, тогда как начало README ещё
представляет Open WebUI основным интерфейсом.

Готовность: существует воспроизводимый исходный отчёт; новые сбои можно отличить
от прежних. Текущие незакоммиченные файлы не потеряны.

### 1. Отделить HTTP от сценариев

Ввести явную сборку приложения и настройки. Перенести `run_chat`, `index_version`,
сохранение загрузки и обработчики заданий в модули сценариев. Разбить маршруты
по чату, документам, заданиям и совместимости OpenAI. Переводить внутренние
ошибки в HTTP в транспортном слое. Существующий `api.app` временно сохранить
как точку входа.

Готовность: HTTP и worker вызывают общий код; адреса, статусы и поля ответов
совместимы с обоими сайтами и существующими клиентами.

### 2. Сделать состояние ответа явным

Оформить типизированные `Evidence`, `AnswerResult` и состояние одного запроса.
Вынести накопление источников, сборку контекста и проверку ответа из замыканий
`answer()`. Сохранить LangGraph на этом этапе. Его замена требует отдельного
обоснования и сравнения поведения.

Готовность: обязательный поиск выполняется даже без решения модели; пустой
повторный поиск не стирает доказательства; метки источников стабильны; дочитывание
одного документа сохраняет другие; исправление ограничено бюджетом; ошибка
необязательного исправления сохраняет первоначальный ответ с предупреждением.

### 3. Выделить хранение и публикацию индекса

Разделить оригиналы, каталог версий, извлечение текста, поиск и публикацию
поколения. Сохранить правило: сначала полная запись поколения в Qdrant, затем
транзакционное переключение указателя и состояния версии в PostgreSQL.
Отдельно определить поведение удаления из поиска при сбое между операциями.
Вынести управление схемой из конструкторов в версионированную процедуру миграции.
SQLite оставить в явно обозначенном режиме миграции/совместимости до проверки
его потребителей и переноса тестов.

Готовность: сбой записи Qdrant сохраняет прежнюю видимую версию; повтор операции
не оставляет противоречивых состояний; оригинал доступен после ошибки;
частичные поколения не попадают в поиск.

### 4. Объединить правила исполнения

Сначала определить идемпотентность сценариев. Сейчас повтор выполнявшегося
чат-задания может повторно записать ход диалога, если процесс упадёт после
сохранения ответа, но до завершения задания. Нужен устойчивый ключ операции и
проверяемая связь результата с заданием.

Затем провести GPU-операции через единый механизм лимитов. Учесть `/chat`,
`/ingest/*`, `/v1/chat/completions` и `/v1/embeddings`: один только перенос worker
в отдельный процесс не ограничивает остальные вызовы. Сохранить повторную
проверку прав перед исполнением и существующее лидерство очереди, пока новая
схема владения ресурсом не проверена. Добавить структурированную диагностику
с идентификаторами задания и этапа, без текста закрытых документов и ключей.

Готовность: проверены сбои до и после сохранения результата, отзыв прав,
перезапуск worker, отмена ожидающего задания и ограничение GPU между процессами.

### 5. Устранить повторную обработку корпуса

Замерить чтение Qdrant, построение BM25, генерацию embeddings и вызовы модели.
По результатам выбрать кэш лексического индекса по поколениям либо постоянное
лексическое хранилище. Соседей и видимость источников получать адресно.
Кэшировать можно только с явной проверкой прав и актуального поколения;
снятие документа с поиска должно инвалидировать соответствующие данные.

Готовность: качество поиска не ниже исходного на согласованном наборе вопросов;
проверены отзыв доступа и смена поколения; ускорение подтверждено замерами на
корпусах разных размеров.

## Как выполнять

Каждый этап — отдельное проверяемое изменение с возможностью возврата.
Не совмещать перенос модулей, изменение алгоритма поиска и смену схемы данных
в одном изменении. До миграций подготовить согласованную резервную копию
PostgreSQL, Qdrant и оригиналов и проверить процедуру восстановления.

Первые действия после выбора варианта Б: этап 0, затем перенос сценария чата
из `api.py` с сохранением существующих точек входа. План не требует немедленной
смены моделей, UI, векторного хранилища или добавления брокера сообщений.

Календарные сроки до исходного прогона и оценки PostgreSQL-покрытия ненадёжны.
Сначала оценить первый завершённый этап, затем уточнять остальные по фактическому
объёму связей и необходимых проверок.
