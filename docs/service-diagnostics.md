# Проверка подключений к сервисам

В консоли API на порту 8000 введите личный ключ с ролью `reader` и нажмите
«Проверить сервисы». Ответ выводится в блоке проверки запроса, включая HTTP 503.
Проверку можно выполнить до загрузки документов и заданий, даже если база недоступна:
введите ключ и нажмите кнопку проверки после ошибки обычного подключения.

`GET /diagnostics/services` и `GET /ready` выполняют одинаковые проверки.
Нужен заголовок `Authorization: Bearer <личный ключ>`.
`GET /health` остаётся открытой проверкой работы самого процесса API.

| Сервис | Проверка |
| --- | --- |
| `postgres` | Подключение по `DATABASE_URL` и `SELECT 1`, без запуска миграций |
| `qdrant` | `GET /readyz` по `QDRANT_URL` |
| `lmstudio` | `GET /models` по `LMSTUDIO_BASE_URL` с ключом `LMSTUDIO_API_KEY`; наличие `CHAT_MODEL` (и `EMBED_MODEL` только при пустом `EMBED_BASE_URL`). При заданном `CHAT_CONTEXT_LENGTH` также сравнение с контекстом загруженного экземпляра через `/api/v1/models` |
| `embeddings` | При заданном `EMBED_BASE_URL` — отдельный `GET /models`, наличие `EMBED_MODEL`; ключ `EMBED_API_KEY` |
| `ocr` | `GET /health` по `OCR_URL`; при пустом адресе статус `disabled` |

Проверки выполняются независимо и параллельно. Таймаут HTTP — 5 секунд на
сетевую операцию; у PostgreSQL ограничены подключение и выполнение запроса
(по 5 секунд). Это не строгий общий срок запроса, например при нескольких адресах базы.
Ответы не кэшируются.

HTTP 200 и `status: ready` означают, что проверки прошли. HTTP 503 и
`status: unavailable` означают, что хотя бы одна проверка не прошла.
Отсутствующий `DATABASE_URL` считается ошибкой; отключённый OCR готовность не нарушает.
Если задан `CHAT_CONTEXT_LENGTH`, выгруженная модель или несовпадение контекста
также означают HTTP 503: код `context_not_applied`. Параметры `CHAT_*`, которые
невозможно применить вместе, дают `invalid_configuration`.

В ответе есть время `checked_at`, список `failed_services` и объект `services`.
Для каждого сервиса возвращаются `status`, понятное сообщение `message` и
длительность `latency_ms`. Для ошибки добавляются `code`, подсказка `hint`,
а для HTTP-ошибки — `http_status`. Например:

```json
{
  "status": "error",
  "code": "connection_failed",
  "message": "Не удалось подключиться к сервису.",
  "hint": "Проверьте запуск сервиса, адрес, порт и доступ из контейнера API.",
  "latency_ms": 12
}
```

Коды: `not_configured`, `connection_failed`, `timeout`, `http_error`,
`models_missing`, `authentication_failed`, `database_missing`,
`database_unavailable`, `invalid_response`, `check_failed`, `context_not_applied`, `invalid_configuration`.
LM Studio возвращает `models.chat` с идентификатором `id` и признаком
`available`; `models.embeddings` присутствует только в прежнем общем режиме.
При отдельном сервисе модель проверяется в `services.embeddings.model`.
При заданном `CHAT_CONTEXT_LENGTH` поле `context` содержит `configured`, `loaded`
и статус `matched`, `mismatch` или `not_loaded`. Применение настройки описано
в [настройках модели](model-configuration.md#контекст-и-применение-изменений).

Сырые исключения, строки подключения, ключи и тела ошибок внешних сервисов
в ответ не включаются. Проверка отражает доступность из среды API:
доступность LM Studio из браузера Windows сама по себе не подтверждает доступ из Docker.

Диагностика не запускает генерацию, эмбеддинги или распознавание и не подтверждает
достаточность памяти для модели, наличие коллекции документов или качество поиска.
Необязательные GitLab и SQL Server, используемые отдельными заданиями, здесь не проверяются.

Маршруты доступны, когда процесс API запущен. Если API не смог запуститься
из-за недоступной базы на этапе инициализации, причину нужно смотреть в журнале контейнера.

Проверено 22 октября 2026 года: общий набор — 235 успешных тестов, 25 пропущены
без тестовой PostgreSQL. В работающем Docker API оба маршрута вернули HTTP 200,
все четыре сервиса — `ok` (до миграции embeddings). Отдельная имитация отказа Qdrant вернула
`connection_failed`, сохранив успешные результаты остальных проверок.
Тесты маршрутов также проверяют HTTP 503, авторизацию и отсутствие секретов в ошибках.

После [миграции на Qwen embeddings](qwen-embedding-migration-20261022.md)
повторно проверены все пять сервисов: HTTP 200, статусы `ok`.
Изолированная подстановка недоступного `EMBED_BASE_URL` вернула
`connection_failed` только для embedding-сервиса; рабочие настройки API не менялись.
Реальные векторы и вопросы проверены отдельно от проверки готовности.
